# v3 Roadmap — Feature Parity, Visual Overhaul, and Differentiators

> **For Claude:** each phase below gets its own detailed task-level plan in `docs/plans/` before implementation. This document sets scope, order, and acceptance gates only.

**Goal:** Take Smart Reporter from a feature-complete single-file HTML reporter to the most capable and best-looking open-source Playwright reporter — closing the parity gaps against ortoni-report, monocart-reporter, and ctrf-io/github-test-reporter, while shipping four capabilities none of them have.

**Architecture:** Replace the template-string HTML generator with a bundled Preact SPA (`src/ui/`) built by esbuild and injected into the report shell. The reporter's job narrows to producing a versioned `ReportData` payload; the SPA owns all rendering. Report data moves behind a data-source abstraction so it can be inlined (default, single file) or emitted alongside the HTML (large suites).

**Tech Stack:** TypeScript, Preact + `@preact/signals`, esbuild, plain CSS with custom properties, vitest, Playwright for UI verification of the report itself.

**Design authority:** `2026-10-08-v3-design-ux.md` owns visual language, layout, and interaction for Phases 1–3, and adds design gates to each.

## Scope decisions

**In scope:** navigation and UX parity, CI surface integrations, code coverage, four differentiators — causal failure timeline, flake forecasting, ownership and routing, agent-ready output — plus local model support (Phase 0.5) and accessibility scanning (Phase 10).

**Non-goals for v3, stated so they are not smuggled in:**
- Extensibility API (`setMetadata()`, `onData`/`onEnd` hooks, custom columns), Mermaid/markdown attachments, HAR viewer. Deliberately deferred; revisit after v3 ships.
- A hosted reports server. `playwright-reports-server` owns that space; Smart Reporter stays a reporter.
- Rewriting the live dashboard (`src/live/`). It keeps its current standalone rendering through v3.

**Compatibility contract, held across every phase:**
- Default output stays a single self-contained HTML file that opens over `file://` with no server.
- `cspSafe: true` keeps emitting companion `.css` and `.js` files. The seam already exists at `src/smart-reporter.ts:682`.
- Every existing `SmartReporterOptions` key keeps its current default and meaning. New behaviour ships behind new keys.
- The Python wrapper under `python/` tracks the same option surface.

## Delivery status (2026-10-08)

All phases are on the `v3` branch for one `3.0.0` pull request. Phase 6 (coverage) merges last.

**Deviations from this plan, with reasons**
- Phase 0: golden snapshots of the 2.x HTML were not kept. The renderer was replaced in the same release, so the data contract is guarded instead by builder tests and by screenshot baselines of the real app on a fixture built from the example suite.
- Phase 0: the byte-identical writer swap was skipped for the same reason. Scale evidence is in `docs/investigations/report-scale.md` (2.x fails at 14,000 tests; v3 writes 98 MB externally).
- Phase 2: the 2.x trace viewer is reused unchanged behind a CSS variable alias layer, not rebuilt. Under an enforced strict CSP it stays inert, as in 2.x.
- Phase 3: the reliability heatmap is a History tab, not a separate view. The retry comparison is in the test detail's Attempts section.
- Phase 4: an anomaly counts up to the end of the failing step (not its start), so a 500 that arrives while an assertion retries is caught. No screenshot preview at the playhead: traces are not mined for frames.
- Phase 0.5: the end-to-end run against a real Ollama is not done (Ollama is not installed); a stub OpenAI-compatible server stands in.
- Phase 5: the sticky PR comment is proven against a fake `gh`; the v3 pull request is the first real run.
- Phase 9: per-test owners live on `TestResultData` and reach `ReportTest` through it.
- Phase 10: `withAccessibility` is restored from an earlier PR #36 commit; the accessibility-tree capture is dropped because Playwright 1.57 removed `page.accessibility`.

**Found, not fixed (pre-existing in 2.x)**
- Quality gates set in reporter options do not change Playwright's exit code. The CLI gate does.
- The report data embeds `aiPrompt` (with an environment snapshot) and network bodies. The agent bundle redacts them; the HTML report does not.

## Phase 0 — Data contract and streaming output

**Goal:** Make the reporter emit a versioned, schema-stable payload and stop building the report as one giant in-memory string.

**Depends on:** Phase −1.

**Deliverables**
- `src/report-data/schema.ts` — a versioned `ReportData` interface (`schemaVersion: 3`) covering run summary, tests, steps, history, clusters, gates, quarantine, and CI info. This is the contract every later phase extends.
- `src/report-data/builder.ts` — builds `ReportData` from collector output, replacing the ad-hoc `HtmlGeneratorData` assembly in `src/smart-reporter.ts`.
- Streaming report writer using `fs.createWriteStream`, writing shell → data → bundle in chunks.
- `assetMode: 'inline' | 'external' | 'auto'` option. `auto` is the default: inline below a size threshold, external above it.
- External mode emits `smart-report-data.js` assigning `window.__SMART_DATA__`, loaded by `<script src>`.
- Golden-output snapshot tests capturing today's rendered report for the `example/` suite, to be diffed against every later phase.

**Steps**
1. Define the schema and write a converter from current internal types, so no collector changes yet.
2. Add the streaming writer behind an internal flag; verify identical bytes against the current writer on the example suite.
3. Flip the writer over, delete the string-concat path.
4. Add `assetMode` and the external-data emitter.
5. Generate a synthetic 10,000-test fixture and measure.

**Acceptance evidence**
- A 10,000-test synthetic run generates a report with no `RangeError: Invalid string length` (closes the class of failure reported in issue #19).
- Peak RSS during generation recorded for 1k / 5k / 10k tests and written into `docs/investigations/`.
- Golden snapshot for the `example/` suite is byte-identical before and after the writer swap in `assetMode: 'inline'`.
- A report generated in `external` mode opens over `file://` with all views populated.

**Traps**
- `fetch()` against a relative path is blocked under `file://` in Chrome. External data must be a `<script src>`-loaded JS assignment, never a JSON file fetched at runtime. This is the single most likely way to ship a report that works on the dev's machine and is blank for users.
- `assetMode: 'auto'` must not silently switch existing users to external output at a threshold they never hit before. Pick the threshold from the measured 10k data, document it, and log the mode on every run.

## Phase 0.5 — Local model support (Ollama)

**Goal:** Let teams run AI failure analysis against a local model with no API key and no data leaving the network.

**Depends on:** nothing. Independent of the whole v3 line; can ship as a 2.x release.

**Sized as small on evidence:** `src/analyzers/ai-analyzer.ts:331` is a self-contained 25-line `callOpenAI` with a hardcoded URL, model, and Bearer header. Ollama serves an OpenAI-compatible `/v1/chat/completions`, so the change is parameterising base URL and model, adding provider detection, and extending two user-facing messages.

**Deliverables**
- `ai?: { provider?, baseUrl?, model? }` in `SmartReporterOptions`, plus `OLLAMA_HOST` and `OLLAMA_MODEL` env detection.
- `callOpenAI` generalised to `callOpenAICompatible(prompt, { baseUrl, model, apiKey? })`; the OpenAI path becomes one caller of it, Ollama another. This also covers any other OpenAI-compatible endpoint (LM Studio, vLLM, a corporate gateway) at no extra cost.
- `isAvailable()` and the no-key tip message updated to mention the local option.
- README section on local model setup.

**Acceptance evidence**
- Unit test asserts the request is sent to the configured base URL with no `Authorization` header when no key is set, and with one when a key is set.
- End-to-end run against a real local Ollama instance producing a failure analysis in the report; screenshot in the PR.
- With Ollama configured and unreachable, the run completes and the report generates with analysis skipped — an AI outage must never fail a test run.

**Traps**
- Provider precedence is already non-obvious (`ANTHROPIC_API_KEY` wins, and `sk-ant-oat` tokens reroute to the Claude CLI — issue #40). Add Ollama at the bottom of that chain and document the full order, or users will set a local model and quietly keep paying a cloud provider.
- Local models are slow. The existing `BATCH_SIZE = 3` loop over failures will stall a run on a large failure set. Add a timeout per call and cap total analysis time.


## Phase 1 — UI build pipeline and design system

**Goal:** Stand up the bundled SPA, the visual language, the Failures inbox, and Insights; delete the legacy Overview code.

**Depends on:** Phase 0, and design phase D2 (signed-off screens).

**Deliverables**
- esbuild build step: `build: tsc && node scripts/build-ui.mjs`, producing a minified IIFE bundle plus a CSS file. *(Delivered early by design phase D1.)*
- `src/ui/` — Preact app, router, signals-based store reading `window.__SMART_DATA__`.
- `src/ui/styles/tokens.ts` emitted to `tokens.css` — the design system: colour, spacing, type scale, elevation, motion. Light, dark, and high-contrast as full sets; the six novelty presets as accent-only swaps. *(Delivered early by design phase D1.)*
- `html-generator.ts` reduced to a shell emitter: `<head>`, injected `<style>`, data script, bundle script.
- App shell, Failures inbox, and Insights built in the SPA per the design document; together they replace Overview. The legacy Overview generator deleted in the same change.

**Steps**
1. Esbuild, build script, and bundle budget — delivered by D1; confirm only.
2. Theme tokens — delivered by D1; confirm only.
3. Build the app shell, router, and store.
4. Build the Failures inbox and Insights. Insights carries every former Overview panel: gates, quarantine, health grade, attention alerts, failure clusters, AI summary.
5. Delete the legacy Overview path.

**Acceptance evidence**
- `npm run build` emits `dist/ui/bundle.js` under a stated size budget; the budget is asserted in CI.
- Playwright UI test opens a generated report over `file://` and asserts the Failures inbox and Insights render every panel with correct counts, in light, dark, and high-contrast.
- All 10 theme presets screenshot-verified.
- `cspSafe: true` still emits companion `.css` and `.js` and the report renders with no inline script.

**Traps**
- Inlining a bundled `<script>` breaks `cspSafe`. Build the external-asset path in this phase, not later.
- Preact plus signals must be bundled, not loaded from a CDN — the report has to work offline.
- Do not run legacy and SPA rendering of the same view side by side. Two owners of one view guarantees drift.

## Phase 3 — Navigation and UX parity

**Goal:** Close the ortoni-report navigation gap.

**Depends on:** Phase 2.

**Deliverables**

**Acceptance evidence**

**Traps**

- The grouping engine is the dependency for Phase 9's group-by-owner. Design it to take a pluggable key extractor now rather than hardcoding five modes.

## Phase 4 — Causal failure timeline (differentiator)

**Goal:** One scrubbable time axis per failed test, correlating steps, network, console, and screenshots, marking the first anomaly that preceded the assertion failure.

**Depends on:** Phase 2. Best delivered right after Phase 3 — it is the visual centrepiece.

**Deliverables**
- `src/analyzers/causal-timeline.ts` — merges step, network, and console events onto one normalised time axis from data already extracted in Phase 0.
- First-anomaly detection: the earliest of a failed request, a console error, or an abnormal step duration occurring before the failing assertion.
- Timeline UI: scrubber, layered lanes, screenshot preview at the playhead, anomaly markers with jump-to.
- The detected anomaly is fed into the AI prompt and the Copy AI Prompt output.

**Acceptance evidence**
- Fixture suite with deliberately seeded failure shapes — a 500 API response, a console `TypeError`, and a slow-step timeout — each asserted to surface the right first anomaly.
- Assertion that no anomaly is claimed when none exists; the timeline still renders.
- Screenshot of the timeline added to the README.

**Traps**
- Playwright step timestamps, trace event timestamps, and network timings use different clocks and origins. Normalise against a single run-start epoch in the analyzer and assert the alignment in tests, or every lane will be visually plausible and wrong.
- "First anomaly" is a heuristic. Label it as a suggestion in the UI; never present it as a diagnosis.

## Phase 7 — Flake forecasting (differentiator)

**Goal:** Name currently-green tests that are trending toward flaky, before they fail.

**Depends on:** Phase 0.

**Deliverables**
- `src/analyzers/flake-forecast.ts` — risk score from duration drift, duration variance, retry-count trend, and recency-weighted outcome instability.
- "At risk" panel in Overview listing tests that passed this run but are trending unstable, each with the signal that triggered it.
- Forecast history recorded per run so the model's own accuracy can be checked later.

**Acceptance evidence**
- Unit tests over synthetic history series: a stable series scores low, a widening-variance series scores high, a short series returns "insufficient history" rather than a number.
- Backtest over the repo's own recorded history showing which tests it would have flagged before they were quarantined.
- Never flags a test with fewer than a stated minimum of runs.

**Traps**
- Scoring on thin history produces confident nonsense. Return an explicit insufficient-data state and render it as such.
- This must not feed the quarantine mechanism. Forecasting is advisory; quarantine stays driven by observed flakiness.

## Phase 8 — Agent-ready output (differentiator)

**Goal:** Let a coding agent pull failures and propose fixes without a human copying prompts.

**Depends on:** Phase 0. Stronger with Phase 4's anomaly data, so prefer shipping after it.

**Deliverables**
- `smart-report-failures.json` — a stable failure bundle: error, code frame, call log, failing step, network and console context, detected anomaly, history, and source file paths.
- `npx playwright-smart-reporter failures --json` for piping into an agent.
- An MCP server exposing the bundle as tools (`list_failures`, `get_failure`, `get_trace_context`).

**Acceptance evidence**
- Bundle schema versioned and validated in a test.
- End-to-end check: run the MCP server against a fixture report and confirm Claude Code retrieves a specific failure with its context.
- Redaction proven — the bundle carries no environment variables, headers, or request bodies matching secret patterns.

**Traps**
- Failure bundles carry request and response data. Redaction is a correctness requirement here, not a nicety, because this output is designed to be sent to a third-party model.

## Phase 9 — Ownership and routing (differentiator)

**Goal:** Turn the report from a list of failures into assigned triage.

**Depends on:** Phase 3's grouping engine.

**Deliverables**
- `src/analyzers/ownership.ts` — maps test files to owners via `CODEOWNERS`, falling back to `git log` on the file.
- Group-by-owner mode in the grouping engine.
- Per-owner notification routing in `NotificationConfig`, so a Slack channel or user is picked by owning team.
- Owner column and per-owner health summary.

**Acceptance evidence**
- Fixture repo with a `CODEOWNERS` file; asserted mapping for glob patterns, nested rules, and unowned files.
- Falls back cleanly with no `CODEOWNERS` and outside a git repository.
- Routing test showing two owners receiving two different notifications from one run.

**Traps**
- `git log` on every test file is slow on large repos. Batch it into a single call and cache per run.
- `CODEOWNERS` glob precedence is last-match-wins, not first. Getting this backwards misroutes silently.
